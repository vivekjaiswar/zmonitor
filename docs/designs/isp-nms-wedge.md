## Problem Statement

The founder brought a 72-section spec calling for a ground-up rewrite of ZMonitor into a full enterprise ISP NMS (NestJS/React/Prisma/Postgres, covering BGP/OSPF, RADIUS/AAA, IPAM, multi-vendor OLT adapters, multi-tenancy, 8 delivery phases). The spec's own stated primary differentiator — "customer impact intelligence" (device fails → derive affected PONs/ONUs/customers/POPs → one root incident instead of an alert storm) — is real and matches ZMonitor's positioning as an ISP-first NMS. The question this session actually resolved was not "what should the platform eventually cover" but "does the evidence justify discarding the shipping v2.8.0 product to get there."

## Demand Evidence

- Named target companies: Jeebr, Aerpace, Microscan — confirmed as potential customers, not committed ones.
- No specific decision-maker identified at any of the three. No confirmed current tool/workaround they're using today.
- Jio was initially cited as evidence, then walked back to "companies like this use NMS platforms" — market/competitive reasoning, not a customer signal (Jio is a carrier-scale operator running its own NMS infrastructure; not a realistic ZennialHub prospect).
- **This is the same gap flagged in the prior design session** (2026-08-04, "Live Geo-Status Map"): pushed twice for a specific customer name and dollar figure, none materialized then either. This is now a repeating pattern across two office-hours sessions a month apart — worth the founder's own attention independent of this doc.

## Status Quo

Not directly asked this session (escape hatch invoked after two rounds of demand-evidence pushback) — but observable from the repo: ZennialHub is already winning/serving ISP customers with the current feature set (SNMP monitoring, OLT/ONT hierarchy phase 1, geo-status map, RBAC, licensing). The three target companies' current tooling is unknown.

## Target User & Narrowest Wedge

No named individual decision-maker yet at Jeebr, Aerpace, or Microscan. The wedge chosen (see Recommended Approach) is deliberately scoped to be small enough to validate against one of these three accounts without multi-quarter commitment: OLT/ONU depth + customer-impact correlation, the spec's own stated differentiator, built as an extension of work already in flight (OLT/ONT hierarchy phase 1 shipped 2026-08-08). The specific fields, UI surface, and which OLT vendor to support first are intentionally left undefined here — they get defined after the discovery call in The Assignment, so they're scoped to what the named contact actually needs rather than guessed at. But the outer ceiling is fixed regardless of what the discovery call turns up: read-only telemetry and status only, no device provisioning or config-write capability, and a single OLT vendor to start. Anything past that ceiling is a new decision, not an extension of this wedge.

Restating the target behavior so it doesn't require re-reading the original spec: when a device fails, walk its known dependents (interfaces → PONs → ONUs → customers → POPs) and emit one root incident carrying the impact summary, instead of one alert per affected leaf node.

## Constraints

- Current stack: Node.js/Express/Socket.IO backend, Vue 3 frontend, SQLite (`db/kuma.db`) — a live Uptime Kuma fork at v2.8.0, not a blank slate.
- Existing plugin architecture (`server/monitor-types/`, `server/notification-providers/`) already supports incremental capability addition — this is how SNMP and OLT/ONT phase 1 shipped without a rewrite.
- Lean-code/YAGNI guidance on file for this project explicitly warns against bloating ZMonitor.
- SQLite is a real ceiling for high-frequency time-series polling at larger device counts, but is not yet the bottleneck at current scale — no evidence was presented that it is today.

## Premises

1. Demand evidence for full enterprise NMS depth is "named target account, no confirmed contact, no confirmed pain" tier — real enough to justify continued ISP-monitoring investment, not strong enough to justify discarding a shipping product for a from-scratch rewrite. **Founder agreed** (selected Approach B after the evidence was laid out plainly).
2. The current codebase already has 5 ISP-relevant features shipped in its last 10 commits; a full rewrite forfeits all of it before any new capability reaches a target account.
3. The 72-section spec's full scope is sized for a funded multi-engineer team over 1-2+ years; it does not fit the current team's capacity or the target accounts' timeline.
4. Approach A (full rewrite) was the founder's stated intent going in ("Yes, full rewrite is intentional") — revised after the demand-evidence questioning surfaced the actual evidence tier. Recorded here so the reversal and its reasoning are traceable, not silently dropped.

## Approaches Considered

### Approach A: Full Rewrite (as specced) — rejected
Greenfield NestJS/React/Prisma/Postgres/VictoriaMetrics platform, all 45+ modules, 8 phases. Rejected: nothing ships to any target account for 1-2+ years; forfeits all live v2.8.0 work; scope doesn't match current team capacity.

### Approach C: Parallel ISP-Ops correlation service — deferred, not rejected
Keep the shipping core as-is; build "customer impact intelligence" as a new service (modern stack) that ingests from ZMonitor via API rather than replacing it. Deferred rather than chosen now because it's still more upfront design/integration work than the evidence currently justifies — worth revisiting if Approach B validates demand and the correlation engine's scope outgrows what fits cleanly in the existing app.

## Recommended Approach

**Approach B: ISP-NMS Wedge on current stack.** Build OLT/ONU depth + customer-impact correlation as new modules in the existing Express/Vue/SQLite app, reusing the existing monitor-types plugin architecture, RBAC, licensing, and the OLT/ONT hierarchy work already shipped. Ships incrementally the same way every recent commit has. Converts "potential customer" into "named customer" fastest — but the sequence is discovery first, build second: The Assignment (a real conversation with a named contact) happens before this scope is locked and built, not after. "Weeks, not years" describes how fast Approach B *can* move once the discovery call confirms what to build — it is not permission to build before that call happens.

If a named contact at one of the three accounts confirms this is the actual blocker and signs on the strength of the deeper capability, that's the evidence to justify a larger platform investment (Approach C next — isolating the correlation engine on a modern stack once it's proven, not before).

## Open Questions

- Who, specifically, is the decision-maker at each of Jeebr, Aerpace, and Microscan? (See The Assignment.)
- What are they using today instead of ZennialHub, and what would it take for them to switch?
- At what device/polling count does SQLite actually become the bottleneck for this wedge? (Not yet measured — don't preemptively solve it.)
- Does the OLT/ONT hierarchy Phase 1 schema already capture customer-to-ONU mapping, or only device hierarchy? Customer-impact correlation needs the former; unverified as of this doc. Check before scoping the build.
- If no named contact materializes at any of the three accounts within the 2-week timebox (see The Assignment): treat that as a finding, not a failure, and revisit whether Jeebr/Aerpace/Microscan are the right wedge before trying other prospects or building anyway on product judgment alone.

## Success Criteria

- A named contact at one of the three target accounts has seen the OLT/ONU + customer-impact correlation capability and stated, specifically, whether it changes their buying decision.
- The capability ships as new modules in the existing app with no schema migration that breaks an existing install without a migration script, and no downtime for currently-running ZennialHub deployments during the upgrade.

## Dependencies

- Builds on OLT/ONT site hierarchy Phase 1 (already shipped 2026-08-08).
- Builds on the existing SNMP monitoring work (already shipped).
