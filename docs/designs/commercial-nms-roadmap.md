## Vision

### 10x Check

The feature-checklist version of this roadmap is "ZMonitor has as many capabilities as Zabbix." The 10x version is different in kind, not degree: ZMonitor becomes the single tool an ISP's ops team actually lives in all day — not one dashboard among several, but the thing that closes the loop from "something's wrong" to "here's exactly what, where, and who it affects" to "here's what to tell the customer." The map isn't a feature, it's the front door. Optical power isn't a metric, it's the "why." The site hierarchy isn't a schema decision, it's what makes "this splitter died" instantly become "these 40 sites/monitors are affected" instead of an ops person figuring that out by hand.

### Platonic Ideal

An ops person at a small ISP — one without a $150k/year senior network engineer on staff — opens ZMonitor once each morning. The map shows problems colored by severity, not just up/down: a yellow pin means "this ONT's signal is degrading, will fail in about two weeks at this rate," not just "still technically up." One click goes from a red pin to the optical-power trend that explains it, to the list of downstream *sites/monitors* affected, to a pre-drafted plain-English outage note ready to send. The tool does the correlation work a skilled engineer would do in their head — instantly, for a team that doesn't have one.

**Correction from adversarial review:** the original draft of this vision said "downstream customers affected." No `customer`/`subscriber` entity exists anywhere in the schema — item 4 (site hierarchy) groups monitors/sites, not end-customers. Corrected above to "sites/monitors." A true per-customer impact view is a real, larger gap (would need a customer↔ONT mapping, which nothing in this plan currently builds) — noted as an open question below rather than silently added to scope.

## Temporal Interrogation — Decisions Locked Now

- **Item 1 (licensing) offline behavior:** grace period (default 14 days) after last successful license check-in, then soft-lock (persistent admin-facing banner, not a functional lockout). Never hard-locks a paying customer's monitoring during a connectivity or billing hiccup.
- **Item 3 (optical power) OID configuration:** vendor dropdown with built-in profiles (Huawei/ZTE/Nokia/Calix to start), not free-text-only. ZennialHub owns maintaining profile accuracy as vendor firmware changes — real ongoing maintenance cost, traded for a much lower support burden per ISP admin.

## 11-Section Deep Review — Decisions Locked

- **1A (Architecture):** licensing needs a server-side global override flag ZennialHub can flip to instantly disable ALL enforcement fleet-wide without a per-customer software update — mitigates a license-server bug false-locking every paying customer simultaneously.
- **2A (Error/Rescue):** license validation uses server-anchored time + a tolerance window, not the customer server's local clock — prevents false lockouts from clock skew on self-hosted boxes.
- **3A (Security):** new site-level endpoints (Item 4) MUST reuse the same RBAC filter pattern `Monitor.getAccessibleMonitorIdsSQL()` already uses — not a parallel permission model.
- **3B (Security):** outage-summary generation (Item 7) MUST reuse `status_page.js`'s existing public/private filtering — never reads raw monitor/site records directly.
- **4A (Data flow):** a fresh install with no license key configured yet defaults to VALID/trial state — the license state machine only starts grace/lock logic once a key actually exists.
- **4B (Data flow):** signal-health pins show a distinct neutral/gray "insufficient data" state until enough readings exist for a stable regression (not a false amber/red from a 2-point trend).
- **5A (Code quality):** vendor OID profiles (Item 3) are delivered/updatable via the same license-check phone-home channel (Item 1), not hardcoded per release — a wrong OID becomes a server-side fix, not a customer upgrade.
- **6A (Tests):** license tokens are short-lived with frequent refresh (not long-lived + a revocation list) — closes the token-replay-after-cancellation gap with less new infrastructure.
- **7A (Performance):** basic marker clustering is in scope for the map (Items 2/8) from the start — cheap now, expensive to retrofit once customers depend on the unclustered view at scale.
- **8A (Observability):** a fleet-wide health dashboard (license check-in status + optical-poll failure rate by vendor) is in scope for Item 1 — turns a systemic issue into one alert instead of a trickle of individual support tickets, sized for a small/solo operating team.
- **9A (Deployment):** the 74 existing production monitors migrate into the new site hierarchy (Item 4) via manual admin assignment, not an auto-grouping heuristic — zero risk of silently misgrouping a live customer's real infrastructure.
- **9B (Deployment):** license enforcement ships feature-flagged OFF first and is verified fleet-wide before being turned on for any customer — a real staged rollout, not just the 1A kill-switch as the only safety net.
- **11A (Design):** the map shows an explicit "map tiles unavailable" state (with a still-functional pin list fallback) if the OSM tile server is unreachable, rather than a blank map that reads as broken.
- **11B (Design):** signal-health pins pair color with a shape/icon distinction (not color-only) for colorblind accessibility.

## Open Questions

- **Per-customer (not just per-site) impact mapping.** The original vision language implied "N customers affected," but no `customer`/`subscriber` entity exists in the schema, and nothing in this plan builds one. If true customer-level impact views matter, that's a real additional scope item (a customer↔ONT mapping) not currently covered — surface it explicitly before assuming item 4/7 deliver it.
- **ONTs with no SNMP/optical telemetry support** (common on cheap consumer-grade units) — item 3 needs an explicit fallback to binary status-only rather than an error or missing pin.
- **GPON-vendor assumption is unverified for the named prospective customer** (per the outside voice) — nothing confirms their network is fiber/GPON rather than DOCSIS/cable or fixed-wireless. Resolve alongside The Assignment, not after building items 3/6.
- **Per-customer onboarding cost (GPS-coordinate collection) is not reflected in any effort estimate** (per the outside voice) — every estimate above is engineering-hours only. If coordinate collection is a manual, per-customer slog, the "cheap wedge" premise may not hold for customer #2 even if customer #1 validates it.
